# MuJoCo 教程开发调试记录：思路、过程与结果

> 本教程并非一帆风顺地写完，而是经历了大量"现象 → 假设 → 验证 → 修正"的调试循环。
> 这份文档完整记录了每一个问题：**看到了什么、为什么这么想、做了什么、结果如何、
> 根因是什么、最终怎么改的**。它既是"踩坑手册"，也是一份"如何系统性调试
> 仿真 / RL 程序"的方法论示例。

---

## 0. 一句话总览

调试中最大的教训是两条：

1. **先验证你的"读数"，再相信你的"结论"**。我们花了很久怀疑"手指与方块接触退化、
   摩擦失效"，最后发现只是把 MuJoCo 接触帧的**法向轴读反了**（法向是第一个轴
   `frame[0:3]`，不是第三个轴）。
2. **仿真里"看起来对"不一定"物理上稳"**。薄手指 + 桌面轻方块的摩擦夹持，在
   MuJoCo 里会因"位置执行器持续向内推→压穿轻物体""球形指尖的楔形效应"等而失败，
   最终改用官方同款**运动学虚拟抓取**（`mj_attachBody` 的功能）保证可靠。

## 2. 入门章（01 / 02）

### 2.1 框架后端：`end_effector` 的 `KeyError`

- **现象**：用 `MuJoCoBackend` 加载倒立摆后调用 `step()`，抛
  `KeyError: Invalid name 'end_effector'`。
- **排查思路**：报错来自 `self._data.body("end_effector")`。原代码用
  `hasattr(self._data, "body")` 判断是否存在该 body。
- **关键洞察**：`data.body` 在 mujoco Python 绑定里**永远存在**（它是一个包装器属性），
  所以 `hasattr` 恒为 `True`，于是无条件调 `data.body("end_effector")`，对没有该命名的
  模型就抛 KeyError。
- **为什么这么改**：判断 body 是否存在，官方做法是
  `mujoco.mj_name2id(m, mjOBJ_BODY, name) != -1`（返回 -1 表示不存在）。
- **修改**（`src/simulation/backends/mujoco.py`）：
  ```python
  has_end_effector = mujoco.mj_name2id(
      self._model, mujoco.mjtObj.mjOBJ_BODY, "end_effector") != -1
  obs["end_effector"] = (self._data.body("end_effector").xpos.copy()
                         if has_end_effector else np.zeros(3))
  ```
- **结果**：任何模型都能正常 `step()`，没有 `end_effector` 的模型返回零向量。
- **预期 vs 实际**：预期是"只对有该 body 的模型读取末端"，实际完全符合。

### 2.2 倒立摆：小车被 10N 推不动

- **现象**：`02_build_cartpole.py` 里给恒定 10N，小车位移几乎为 0。
- **排查思路**：先查执行器力 `qfrc_actuator[0]=10N`（正确），再查加速度
  `qacc[0]≈1e-6`（几乎为 0）→ 必有巨大反力。
- **根因**：小车 `pos="0 0 0"` 与轨道 `rail`（z=-0.03、半高 0.02，顶面 z=-0.01）
  在几何上**相互穿透**（小车底面 z=-0.06 < 轨道顶面 -0.01），接触解算器产生极大
  正压力，摩擦把小车"粘"在轨道上，10N 推不动。
- **为什么这么改**：避免接触干扰的最干净做法是让小车**悬空**，只用 `slide` 关节
  约束在 1D 轨道上（轨道仅作视觉）。
- **修改**：小车移到 `pos="0 0 0.15"`，删除穿透的 rail geom，加一个纯地面 plane。
- **结果**：10N 正常把小车推 1.0m。
- **教训**：**"几何看起来贴在一起"在 MuJoCo 里 = 接触力爆炸**，宁可留间隙。

### 2.3 倒立摆：摆杆不会自己倒下

- **现象**：无控制时摆杆角度保持 0°。
- **根因**：θ=0 恰好是**不稳定平衡点**（完美直立、零速度），对称性使得它永远
  不会动。这是物理属性，不是 bug。
- **修改**：被动演化演示前设 `data.qpos[1] = deg2rad(5)`。
- **结果**：摆杆正常倒下。
- **教训**：演示"重力作用"时要避开平衡点。

## 3. 控制章（04）

### 3.1 起摆后停在"下摆位"

- **现象**：`04_pendulum_swingup.py` 跑完，摆杆停在"距直立 179°"（即下垂）。
- **排查思路**：打印物理量发现"目标能量"和"直立判定"都是按 θ=0=下垂、θ=π=直立
  写的，但**模型里 θ=0 就是直立**（摆杆沿 +Z）。
- **根因**：控制公式与模型的**角度基准不一致**——公式把 θ=0 当下垂，模型 θ=0 是直立。
- **修改**：统一以 **θ=0 = 直立** 重写：能量 $E=\tfrac12 I\omega^2+mgL\cos\theta$、
  目标 $E^*=mgL$、PD 锁定围绕 θ=0。
- **结果**：起摆逻辑正确，但此时初始就在直立（PD 直接锁定，没展示"起摆"），
  于是再把初始 `qpos[0]=π`（下垂）→ 完整展示"从下垂泵到直立"。

### 3.2 泵能公式 `sign(ω·cosθ)` 不起摆

- **现象**：即使公式"看起来标准"，摆杆始终在小幅摆动，能量不累积。
- **排查思路**：做四组合符号实验，全部失败；再用手推 `dE/dt = u·ω` 推导，
  发现 `sign(ω·cosθ)` 在底部附近（cosθ≈-1）等价于 `-sign(ω)`，**是纯阻尼**。
- **根因**：教科书公式 `u=k(E*-E)sign(ω·cosθ)` 的 cos 项是为了"过顶不加油"，
  但作为**从静止下垂起摆**的激励项是错误的；从底部起摆需要 `sign(ω)`。
- **为什么这么改**：由 $dE/dt=u\,\omega$，能量不足时令 u 与 ω 同号即可持续泵能，
  过冲时自动反向制动（能量整形本质）。
- **修改**：`u = kp*(E_star - E)*sign(ω)`；并加**双门限**切换 PD：
  角度 $|\theta|<0.4$ **且** $|E-E^*|<0.25E^*$ 才锁定（只靠角度会误锁"路过直立"的摆）。
- **结果**：单摆从下垂 2 秒内泵到直立并锁定（偏差 < 1°）。
- **教训**：**先做符号/相位的手推实验，再写进代码**；"标准公式"有适用前提。

### 3.3 mujoco 3.9 API 变更

- **现象**：`jnt_inertia`、`body_com` 报 `AttributeError`。
- **根因**：mujoco 3.x 移除了 `jnt_inertia`，质心改在 `body_ipos`（body 系偏移），
  转动惯量用 `body_inertia`。
- **修改**：$I=\text{body\_inertia}[1,1]$（绕铰链轴）、$L=\|\text{body\_ipos}[1]\|$。
- **结果**：物理常量正确。

## 4. 渲染章（05）

### 4.1 相机注入报"重复 worldbody"

- **现象**：往模型字符串注入 `<camera>` 时报
  `Schema violation: unrecognized element 'worldbody'`。
- **根因**：MJCF 只允许一个 `<worldbody>`，我把整个 `<worldbody><camera/></worldbody>`
  又塞进了已有的 worldbody。
- **修改**：只把 `<camera>` 元素插到现有 `</worldbody>` 之前。
- **后续坑**：`Renderer` 必须在**最终模型**（含相机）确定后创建，否则
  `update_scene(data, camera="track")` 找不到相机。
- **结果**：跟随相机正常，视频录制成功。

## 5. 项目实战：抓取（06 / 07）—— 本次最曲折的部分

### 5.1 DLS-IK 不收敛

- **现象**：IK 结果偏差巨大（目标 [0.25,0,0.48]，实际 [0.01,0,0.27]）。
- **根因**：原实现只做**一次** DLS 求解且步长无限幅，误差大时一步过冲。
- **修改**：迭代求解（每轮重算雅可比）+ `step_max=0.1` 限幅 +
  误差 < 2e-4 提前退出。
- **结果**：任意可达点误差 < 0.2mm。附带发现 `n_iter=40` 不够（约需 50+ 次），
  把默认提到 100。
- **教训**：IK 是"迭代逼近"，不是"一步到位"。

### 5.2 机械臂被自己卡住（自碰撞）

- **现象**：关节明明有目标，却被"锁"在某个角度（`shoulder_pitch` 用 255 N·m
  也顶不过去）。
- **排查思路**：打印接触对 → 看到 `shoulder_geom<->base_geom`、
  `upper_arm_geom<->base_geom`。
- **根因**：相邻连杆在关节附近几何必然重叠（肩球体与基座柱），MuJoCo 把它们当
  成碰撞，机器人被自己的"身体"卡住。
- **修改**（`robot_arm.xml`）：加 `<contact><exclude body1="base" body2="..."/></contact>`
  排除基座与手臂各段、以及手指与前臂/腕/夹爪基座的自碰撞。
- **结果**：机械臂自由运动，伺服收敛。
- **教训**：**MJCF 里相邻连杆的 `<exclude>` 几乎是必须的**。

### 5.3 肘部碰桌面，抓不到方块

- **现象**：IK 可达，但物理伺服后末端停在较高处（z≈0.55 而非 0.48），且
  `elbow_geom<->table`。
- **根因**：肩部安装太低（0.6m），手臂下探时**肘部落到桌面以下**，被桌面挡住。
- **修改**：基座柱加高，肩关节抬到 **0.85m**；顺带让手臂以"肘高"姿态工作。
- **结果**：无碰撞到达抓取点，伺服误差降到 2mm。

### 5.4 夹爪朝上（指尖在方块上方）

- **现象**：指尖 z=0.52，方块顶才 0.46——夹爪根本没够到方块。
- **排查思路**：打印夹爪局部 X 轴的世界方向 = `[0,0,1]`（朝上）。
- **根因**：`wrist_pitch = -π/2-(θ1+θ2)` 符号反了。推导：腕部局部 X 方向由累计
  俯仰角 $\phi=\theta_1+\theta_2+\theta_3$ 决定，$R_y(\phi)\hat x=(\cos\phi,0,-\sin\phi)$；
  要朝下(-Z)需 $\phi=\pi/2$，故 $\theta_3=\pi/2-\theta_1-\theta_2$。
- **修改**：公式符号取反。
- **结果**：夹爪朝下，指尖落在方块中平面。

### 5.5 摩擦夹持抬不起方块（核心攻坚）

这是花费最多时间的部分，完整记录如下。

#### 5.5.1 现象
手指明明包住方块（接触存在、法向力 5.8N、摩擦系数 1.2），但腕部一抬升，方块纹丝不动。

#### 5.5.2 逐层排查（关键证据）
1. **先查"手指是否接触方块"**：`mj_contactForce` 显示有接触、法向力存在 → 排除"没碰上"。
2. **再查"摩擦是否生效"**：对方块直接施加 5N/12N 向上力，方块不动；
   而方块单独（无手指）加 20N 能起飞 → 说明**手指在"按住"方块**，摩擦其实有效！
3. **追踪抬升**：腕部 z 从 0.47 升到 0.60，方块 z 恒为 0.42，且**手指 qpos 从 0.014
   变到 0.026**——手指不是"张开"，而是**继续向内闭合、压穿方块**（内表面从 ±0.014
   越到 ±0.002，穿过了方块中心）。
4. **接触帧误读（最大弯路）**：早期打印接触法向，看到 `frame[6:9]=[1,0,0]` 就断定是
   "X 法向的退化边缘接触"。直到用一个"方块放桌面（法向必为 +Z）"的最小场景验证，
   才发现**法向其实是 `frame[0:3]`（第一个轴）**！之前的"退化接触"判断全部作废——
   接触一直是正确的 Y 法向。

#### 5.5.3 根因小结
- 薄盒手指与方块接触会因"手指太薄/边缘"产生不稳定接触；
- 高 kp 的 position 执行器会**持续向内推，把 0.05kg 的轻方块压穿**；
- 球形指尖又引入**楔形效应**（球面法向带向下分量，把方块向下楔死）；
- 即便用对读数、把夹持力调到 138N，抬升时手指仍会压穿方块而失效。

#### 5.5.4 为什么最终用"运动学虚拟抓取"
真实摩擦夹持需要极其精细的接触调参（面积、刚度、夹持力、抬升速度），对教程来说
既脆弱又难复现。MuJoCo 官方演示解决"演示抓取"用的是 `mj_attachBody`（把物体动态
"焊"到夹爪）。本版本 Python 绑定未暴露该函数，于是用等价的**运动学同步**：
抓取后每步把方块 freejoint 的位置同步到夹爪 + 固定偏移（`mj_forward` 更新）。

#### 5.5.5 如何修改
- `06_pick_place_env.py` 新增：
  ```python
  def attach_block(self):        # 记录偏移，进入虚拟抓取
      self._attached_offset = block.pos - gripper.pos
  def release_block(self):       # 解除
      self._attached_offset = None
  def _sync_block(self):         # 每步同步位置（在 move_ee_to / record 中调用）
      if self._attached_offset is not None:
          self.data.qpos[jadr:jadr+3] = gripper.pos + self._attached_offset
          mujoco.mj_forward(self.model, self.data)
  ```
- `07_scripted_pick_place.py`：在 grasp 阶段结束后 `attach_block()`，release 阶段
  `release_block()`。
- 同时在教程 README 里**如实写明**了这段经验（接触帧读取、压穿、楔形效应、
  虚拟抓取原理）。

#### 5.5.6 结果与预期
- **结果**：方块随夹爪精确抬起（z→0.65）、搬运到目标上方、下放置（误差 1.6cm），
  任务 100% 成功；生成 `pick_place_demo.mp4`。
- **预期 vs 实际**：预期"摩擦夹持完美工作"，实际"薄手指+轻方块在 MuJoCo 中不可靠"；
  最终通过"承认物理现实 + 换可靠机制"达成比预期更稳的结果。

## 6. 项目实战：PPO（08 / 09）

### 6.1 后端工厂为空
- **现象**：`SimBackendFactory().create("mujoco", ...)` 报"未知后端"。
- **根因**：框架的工厂只提供 `register`，没有任何地方把内置后端注册进去（文档与实现不一致）。
- **修改**：给 `SimBackendFactory` 加 `default()` 类方法，内部注册 MuJoCo/PyBullet；
  保持 `__init__` 为空（不破坏已有测试"新工厂为空"的断言）。
- **结果**：`SimBackendFactory.default().create("mujoco", ...)` 正常创建后端。

### 6.2 PPO 训练四连 bug（框架）
1. `compute_gae` 对 bool 张量做 `1 - dones` → 修复：`dones = dones.float()`。
2. buffer 里 obs 用 `torch.cat`（展平了环境维）而 actions 用 `torch.stack`
   （保留环境维），维度不一致 → 修复：全部展平为 `(T*N, ...)`（obs 用 cat，
   其余 reshape）。
3. `train_step` 把 `total_loss` 用 `.item()` 转 float，`train_on_buffer` 却要
   `loss.backward()` → 修复：`total_loss` 保留张量。
4. `collect` 把带计算图的 `log_prob/value/action` 存入 buffer，更新时 backward
   穿透旧采样图报"重复反向传播" → 修复：存入前 `.detach()`（含 `last_value`）。
- **排查方法**：每修一个就重跑 5 轮最小训练，让错误"逐一浮出水面"，避免一次改太多。
- **结果**：训练约 2 分钟收敛，评估回报从 ~170 升到**满分 800**；`09` 加载策略
   平衡倒立摆并录成 `cartpole_balance.mp4`。

## 7. 方法论沉淀

这套调试过程可以提炼成可复用的排查流程：

1. **先修"读数"，再下结论**：任何"接触/受力/法向"结论，先用一个已知答案的最小
   场景验证读取方式是否正确（如"方块放桌面法向必为 +Z"）。
2. **隔离变量**：一个问题拆成多个小实验（接触是否存在 → 摩擦是否生效 → 力到哪去了），
   每步只看一个量。
3. **用物理守恒校验**：`dE/dt = u·ω`、力的平衡、`qfrc_constraint` 等"守恒/平衡"
   约束能快速发现"读数对不上"的矛盾点。
4. **先手推符号，再写代码**：控制律的相位/符号问题，动手算一遍比盲试快。
5. **接受物理现实**：某些机制（薄手指+轻物摩擦夹持）在数值仿真里就是不可靠，
   换一个**机械上保证成立**的机制（虚拟抓取、互锁、托举）比硬调参数更稳。
6. **改一次测一次**：RL 训练出现多个错误时，逐个修复并最小化复现，避免"改完一堆
   不知道是谁修的"。
